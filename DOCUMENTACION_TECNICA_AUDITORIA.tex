\section{Descripción General del Sistema}

El sistema de gestión de tickets constituye una plataforma web servidor-renderizada que facilita la creación y seguimiento de solicitudes de soporte técnico. Integra tres portales diferenciados: acceso público sin autenticación para creación de tickets mediante número de ficha y nombre, panel de usuario autenticado para consulta y seguimiento de tickets propios, y panel administrativo restringido para personal de tecnología encargado de asignación y resolución de incidencias. La arquitectura implementa separación de responsabilidades mediante ruteador API centralizado y endpoints especializados, autenticación basada en sesiones PHP, almacenamiento relacional en MySQL, y generación de reportes en formato Excel. El flujo operativo contempla identificación del solicitante, creación de ticket con categorización y priorización, visualización de personal IT disponible, asignación a técnico responsable, seguimiento del estado de resolución, y captura de satisfacción del usuario.

\section{Estructura del Proyecto}

La organización de archivos responde a la siguiente jerarquía:

\begin{itemize}
    \item \texttt{/config/}: Módulo de configuración centralizada. Contiene \texttt{database.php} con clase de conexión PDO y funciones globales de sesión y utilidades de formato.
    \item \texttt{/api/}: Directorio de endpoints JSON. Incluye \texttt{tickets.php} (CRUD autenticado), \texttt{tickets\_admin.php} (operaciones administrativas), \texttt{tickets\_publico.php} (endpoints públicos), \texttt{reportes.php} (generación de reportes Excel).
    \item Raíz del proyecto: Archivos de vistas renderizadas servidor. \texttt{index.php} (portal público), \texttt{login.php} (autenticación), \texttt{dashboard.php} (panel usuario), \texttt{admin.php} (panel administrativo), \texttt{api.php} (ruteador central alternativo).
    \item \texttt{/uploads/}: Directorio para almacenamiento de archivos adjuntos de tickets (estructura creada dinámicamente).
    \item \texttt{/vendor/}: Dependencias Composer (PhpSpreadsheet, Firebase JWT, Google Auth).
\end{itemize}

\section{Flujo de Operación General del Sistema}

\subsection{Portal Público}

\begin{enumerate}
    \item Usuario ingresa número de ficha y nombre completo en formulario de identificación.
    \item Sistema valida existencia de tickets mediante endpoint \texttt{api/tickets\_publico.php?action=mis-tickets}.
    \item Se carga lista de tickets del usuario con estado y detalles.
    \item Usuario puede crear nuevo ticket mediante formulario con título, descripción, prioridad, categoría y archivos adjuntos.
    \item Sistema envía datos a \texttt{api/tickets\_publico.php?action=crear} mediante POST con FormData.
    \item Endpoint valida campos requeridos, crea registro en tabla tickets y archivos adjuntos.
    \item Se obtiene estado actual de personal IT disponible mediante \texttt{api/tickets\_publico.php?action=personal-it}.
\end{enumerate}

\subsection{Portal de Usuario Autenticado}

\begin{enumerate}
    \item Usuario autentica con email y contraseña en \texttt{login.php}.
    \item Endpoint \texttt{login.php} valida credenciales, hashs de contraseña y crea sesión con \texttt{\$\_SESSION['usuario\_id']}.
    \item Se redirige a \texttt{dashboard.php} que consume \texttt{api/tickets.php?action=mis-tickets}.
    \item Se cargan estadísticas mediante \texttt{api/tickets.php?action=estadisticas}.
    \item Usuario visualiza lista de tickets propios con opción de ver detalle en modal.
    \item Puede enviar satisfacción mediante endpoint POST a \texttt{api/tickets.php?action=cerrar}.
\end{enumerate}

\subsection{Panel Administrativo}

\begin{enumerate}
    \item Técnico IT autentica con email y contraseña en \texttt{admin.php}.
    \item Sesión se crea con \texttt{\$\_SESSION['admin\_id']}.
    \item Sistema carga lista de todos los tickets mediante \texttt{api/tickets\_admin.php?action=todos}.
    \item Técnico toma asignación de ticket mediante \texttt{api/tickets\_admin.php?action=tomar\&id=X}.
    \item Se actualiza estado de ticket a \texttt{en\_proceso} y usuario a \texttt{ocupado}.
    \item Técnico ingresa resolución mediante \texttt{api/tickets\_admin.php?action=resolver\&id=X}.
    \item Sistema actualiza estado a \texttt{resuelto}, técnico regresa a estado \texttt{disponible}.
\end{enumerate}

\section{Seguridad Implementada}

\subsection{Autenticación}

Sistema implementa autenticación basada en sesiones PHP mediante \texttt{session\_start()} con validación de \texttt{\$\_SESSION['usuario\_id']} en endpoints autenticados. Las contraseñas se almacenan con hash mediante \texttt{password\_hash()} con algoritmo \texttt{PASSWORD\_DEFAULT}.

\subsection{Autorización}

Validación de rol mediante \texttt{\$\_SESSION['rol']} para diferenciación entre usuarios solicitantes y personal IT. Endpoints administrativos validan \texttt{\$\_SESSION['admin\_id']} previo a operaciones.

\subsection{Prepared Statements}

Todas las consultas SQL utilizan prepared statements con bindParam para prevención de inyección SQL.

\begin{lstlisting}[language=PHP,caption={Ejemplo de prepared statement}]
$stmt = $db->prepare("SELECT * FROM usuarios WHERE email = ?");
$stmt->bindParam(1, $email);
$stmt->execute();
\end{lstlisting}

\subsection{Validación de Entrada}

Validación de campos requeridos antes de inserción o actualización mediante verificación de vacío y trimming de espacios.

\subsection{CORS}

Headers CORS configurados en \texttt{api.php} para permitir acceso desde origen especificado.

\begin{lstlisting}[language=PHP,caption={Headers CORS}]
header('Access-Control-Allow-Origin: *');
header('Access-Control-Allow-Methods: GET, POST, OPTIONS');
\end{lstlisting}

\section{Gestión de Archivos Adjuntos}

Archivos adjuntos se almacenan en directorio \texttt{/uploads/tickets/} con validación de tipo MIME y tamaño máximo de 100MB por archivo. Extensiones permitidas incluyen imágenes (jpg, jpeg, png, gif, webp), documentos (pdf, doc, docx, xls, xlsx, ppt, pptx, txt) y video (mp4, avi, mov, wmv, flv, webm).

\begin{lstlisting}[language=PHP,caption={Configuración de archivos}]
$upload_config = [
    'max_file_size' => 100 * 1024 * 1024,
    'allowed_types' => ['jpg', 'jpeg', 'png', 'pdf', 'doc', 'docx', ...],
    'upload_path' => __DIR__ . '/uploads/tickets/'
];
\end{lstlisting}

\section{Modelo de Datos}

\subsection{Tabla usuarios}

Almacena información de usuarios del sistema con campos: id (clave primaria), nombre, email (único), password (hasheado), rol (it o solicitante), estado (disponible, ocupado, ausente), ultimo\_acceso (timestamp).

\subsection{Tabla tickets}

Registro central de solicitudes con campos: id (clave primaria), numero\_ficha, solicitante\_nombre, titulo, descripcion, prioridad (urgente, alta, media, baja), categoria, estado (abierto, en\_proceso, resuelto, cerrado), asignado\_a (referencia a usuarios.id), fecha\_creacion, fecha\_asignacion, fecha\_resolucion, fecha\_cierre, resolucion (texto), satisfaccion (satisfactoria, insatisfactoria).

\subsection{Tabla archivos\_adjuntos}

Registro de archivos asociados con campos: id (clave primaria), ticket\_id (referencia a tickets.id), nombre\_archivo, ruta, fecha\_carga, tipo\_mime.

\subsection{Tabla fcm\_tokens}

Almacena tokens de Firebase Cloud Messaging para notificaciones push con campos: id (clave primaria), token (único), created\_at, last\_used.

\section{Observaciones Técnicas Finales}

\subsection{Arquitectura}

El sistema implementa arquitectura de tres capas: capa de presentación (vistas HTML/PHP), capa de lógica (endpoints API), capa de datos (PDO a MySQL). No existe separación explícita de modelos mediante ORM, utilizándose consultas SQL directo mediante PDO.

\subsection{Manejo de Errores}

Los errores de base de datos se capturan mediante try-catch en operaciones transaccionales. Los errores de validación se reportan mediante respuestas JSON con clave \texttt{success} booleana y mensaje descriptivo.

\subsection{Transacciones}

Operaciones críticas como asignación y resolución de tickets implementan transacciones explícitas mediante \texttt{\$db->beginTransaction()} y \texttt{\$db->commit()}/\texttt{rollback()}.

\subsection{Logs}

Sistema implementa logging mediante archivo \texttt{api\_debug.log} en directorio raíz con timestamps y mensajes de operación crítica.

\subsection{Validación de Cliente}

El código JavaScript valida campos requeridos antes de envío mediante verificación de trim y valor vacío. Las validaciones críticas se replican en servidor.
